This does half the job. The other half is keepalived on the nodes, which this application does not configure. No node carries the address until someone adds it to the virtual_ipaddress block, and until then no traffic reaches the frontend however correct the generated configuration is. A source address must sit in the same block as its VIP, or replies after a failover go to a node that no longer carries the traffic.

Default virtual address

Where an object lands when it names no VIP of its own.

Changing this moves traffic for sites nobody touched. Every object that never named a VIP follows the default, so this is the one change on the page that alters where existing traffic lands. It will ask again before writing, and say how many objects come with it.

Source addresses

What an object may leave from instead of the one its VIP pairs with.

HAProxy takes the source per backend rather than per listener, so a site may leave from a different address than the one it arrived on. Each VIP above already names a default; this table is for the exception, and an exception should have to be named. A NetScaler calls these SNIPs.

Address groups

Named sets an object may restrict itself to with allow_from.

The object names the group; which addresses that is stays here. That way the same object means the same thing in a rehearsal cluster and in production. An object may also write an address or range directly, for what belongs to one site alone.

What is not on this page

And why it is not.

The vip line that deploy checks node ownership against stays in the engine's own configuration and is not editable here. A control the interface can rewrite is not a control. The same applies to paths, identities, keys, the resolvers section and the certificate allowlist: they describe how the system runs rather than what is published on it.
